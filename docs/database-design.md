# Database Design — Adelaide Tambo Digital Visitor Register

## 1. Database Overview

The system will use PostgreSQL to store visitor registrations, selected library activities and administrator accounts.

The database must support group registrations, individual activity counts, secure administrator access and daily, monthly and yearly reporting.

## 2. Database Tables

### visitor_registrations

| Column | Data Type | Constraints |
|---|---|---|
| id | UUID | Primary Key |
| initials_surname | VARCHAR(150) | NOT NULL |
| visitor_count | INTEGER | NOT NULL, greater than 0 |
| registered_at | TIMESTAMPTZ | NOT NULL, default current timestamp |

### activities

| Column | Data Type | Constraints |
|---|---|---|
| id | INTEGER | Primary Key |
| category | VARCHAR(50) | NOT NULL |
| name | VARCHAR(100) | NOT NULL |
| is_active | BOOLEAN | NOT NULL, default TRUE |

Initial activity options:

- Public facilities: Study, Reading, Research.
- IT facilities: Internet, Gaming, Typing.
- Library facilities: Book borrowing, Booking, Other approved services.

### registration_activities

| Column | Data Type | Constraints |
|---|---|---|
| id | UUID | Primary Key |
| registration_id | UUID | Foreign Key to visitor_registrations |
| activity_id | INTEGER | Foreign Key to activities |
| activity_visitor_count | INTEGER | NOT NULL, greater than 0 |

The combination of registration_id and activity_id must be unique.

### admin_users

| Column | Data Type | Constraints |
|---|---|---|
| id | UUID | Primary Key |
| username | VARCHAR(100) | NOT NULL, UNIQUE |
| password_hash | TEXT | NOT NULL |
| created_at | TIMESTAMPTZ | NOT NULL, default current timestamp |

Passwords must be securely hashed and never stored as plain text.

## 3. Relationships

- One visitor registration can have multiple registration activities.
- One activity can belong to multiple visitor registrations.
- The registration_activities table connects registrations and activities.
- Administrator accounts are independent of visitor registrations.

## 4. Business Rules

1. Every registration must have initials and surname.
2. Every registration must have a visitor count of at least one.
3. A registration may represent multiple visitors.
4. Visitors may select multiple activities.
5. Each selected activity must have its own visitor count.
6. Each activity count must be at least one and cannot exceed the registration's total visitor count.
7. Activity counts may overlap because the same visitor may use multiple facilities.
8. The total number of visitors must be calculated from visitor_count, not by summing activity counts.
9. Registration timestamps must be generated by the server.
10. Only authenticated administrators may view registrations and reports.
11. Registration data must be protected against unauthorized access.

## 5. Reporting

### Daily
- List of registrations for the selected day.
- Total visitor count.
- Visitor counts by activity.

### Monthly
- Total visitors for the selected month.
- Daily totals within that month.
- Activity totals.
- Downloadable PDF report.

### Yearly
- Total visitors for the selected year.
- Monthly totals within that year.
- Activity totals.
- Downloadable PDF report.

## 6. Proposed Database Indexes

- Index visitor_registrations.registered_at for date-based reporting.
- Index registration_activities.registration_id.
- Index registration_activities.activity_id.
- Unique index on registration_activities(registration_id, activity_id).
- Unique index on admin_users.username.

## 7. Important Implementation Notes

- Use database transactions to save a registration and its activities together.
- Validate activity counts against the registration visitor count in the backend.
- Use parameterized database queries or a safe ORM.
- Store timestamps with time zone information and report according to the library's local date.
- Prevent duplicate submissions from repeated taps on the iPad.
- Define an approved data retention and backup policy before deployment.
- Confirm the final PDF report layout with the supervisor.
